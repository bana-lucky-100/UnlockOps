# 승인 에이전트의 RAG 문서와 적용 범위

점검 기준: 2026-10-23 저장소의 시나리오 v4, 회사 정책 묶음 revision 3.
사내 규정·공식 요약 28개 문서의 본문, 회사별 생성 묶음, MCP 검색, 승인 분석·보고서 코드를 대조했다.
공식 제품 문서·가격의 최신성을 외부 사이트에서 재검증한 작업은 아니다.

## 현재 자료의 역할

| 자료 | 쓰임 | 확정할 수 없는 것 |
|---|---|---|
| `data/phase2/policies/policy_corpus.md`의 POL-01~14 | 자격, 최소 권한, 예산, 승인·검증 기준의 근거 | 특정 직원의 현재 TF 소속·잔여 예산·현재 권한 |
| 같은 파일의 OFF 문서 14개 | 제품 역할·좌석·기능·전제조건의 설명 | 회사의 승인 허가, 현재 계약가, 실제 적용 성공 |
| `company-*-policy-v3.md`의 FLOW | 회사별 순차 승인 경로 | 실제 담당자 ID와 승인 완료 여부 |
| 같은 묶음의 BASELINE | 시연 범위, 금액 출처와 해석 제한 | 실제 계약·실제 절감·실제 회수 완료 |
| 서버 context·assessment·review_facts | 직원·계정 관측, 확정 판정, 선택 권한, 조회 시점 예산·가격 | 조회 시점 이후에도 조건이 유지된다는 보장 |
| `agent/unlockops/access/approval-review-guide.md` | 승인자별 검토 항목, 사실·근거 구분, 보고서 작성 | 새 회사 정책·새 권한·승인 단계의 신설 |

POL과 OFF의 문서 ID·버전은 article에 보존된다. DB의 회사별 정책 묶음 revision·문서 ID·해시는 별도로 보존한다.
`data/policy_corpus.md`와 `data/company-a-access-matrix.md`는 단일 승인 v1 경로의 자료이다.
Phase 2는 해당 파일을 직접 검색하지 않으며, v1의 직급 상한·승인자를 v2에 섞지 않는다.

## 전체 문서 점검

| 문서 ID | 승인에서 확인하는 내용 | 적용 시 주의점 |
|---|---|---|
| POL-01 | 최소 권한, 순차 승인, 본인 승인 금지, 사후 조회 | 보고서는 승인·실행을 대체하지 않음 |
| POL-02 | TF 소속·전용 자원·비구성원 | 소속은 문장·사용자 주장 대신 서버 사실로 확인 |
| POL-03 / GH-OFF-01·02 | GitHub 저장소 역할과 팀 멤버십 | Copilot 좌석 신청에는 저장소 역할 근거를 섞지 않음 |
| POL-04 / JR-OFF-01·02 | Jira 역할·프로젝트 권한과 제품 접근의 차이 | 공식 진단 힌트의 Admin 조치를 자동 승인 권한으로 해석하지 않음 |
| POL-05 / SL-OFF-01·02 | Slack 채널 참여와 외부 게스트 | 외부 게스트는 문서의 확장 항목, 현재 시연 지원으로 설명하지 않음 |
| POL-06 / GH-OFF-03 | 허용 직군, 예산, 중복 권한·좌석 | 회수 조항은 승인 보고서에서 제외; 공식 정가와 서버 단가 구분 |
| POL-07 | Admin 제외, 구두 승인 무효, 근거 부족 | 최소 권한 제안과 원래 상위 권한 허가를 구분 |
| POL-08 / NT-OFF-01 | Notion 등급·공유·편집 권한 | 기밀 편집 추가 승인은 후속 확장; 현재 경로에서 보장하지 않음 |
| POL-09 / SN-OFF-01 | Snowflake USAGE, 데이터 접근 전제, 사용량 가정 | USAGE를 OPERATE·MODIFY·데이터 접근으로 확대하지 않음 |
| POL-10 / DB-OFF-01 | Databricks 노트북 편집·작업 실행 | 요청자와 Run as 실행 주체의 데이터 접근을 구분; 원문의 소유자 표현을 모든 실행에 일반화하지 않음 |
| POL-11 / SF-OFF-01 | Salesforce 담당 고객·영업 기회 범위 | 전체 조회·삭제·내보내기로 확대하지 않음 |
| POL-12 / DD-OFF-01 | Datadog 서비스 로그·대시보드 조회 | Read Only만으로 서비스별 제한 설정까지 확인한 것으로 쓰지 않음 |
| POL-13 / TB-OFF-01 | Tableau 라이선스·콘텐츠·데이터 원본 | Explorer로 새 데이터 원본 게시가 가능하다고 쓰지 않음 |
| POL-14 / FG-OFF-01 | Figma 파일 편집과 Full 좌석 | 무료 View가 문서에 있어도 카탈로그에 없으면 실행 가능한 대안으로 제안하지 않음 |

규정 원문은 보존했다. 문서를 늘려도 서버의 자격·가격·승인 경로가 자동 확장되지는 않는다.
향후 규칙 변경은 새 immutable revision과 서버 검사·평가를 함께 변경해야 한다.

## 이번 보완과 에이전트 연결

1. **보고서 지침 추가**: 역할별 검토, 출처 우선순위, 비용 구분, 정보 부족, 최소 권한, 지원 범위 제한을 작성·내용 검토 프롬프트 양쪽에 전달한다. 설치 패키지에도 지침을 포함한다.
2. **승인 근거 선택**: 회사·플랫폼이 고정된 검색과 정확 조회를 유지하면서 POL-06 제5조·POL-02 제4조·회수 BASELINE을 제외한다. GitHub 좌석은 Copilot 자료, 저장소는 저장소 역할·팀 접근 자료로 구분한다. TF가 필요하지 않은 자원에서는 TF 규정을 제외한다.
3. **인용 경계 보강**: article과 실제 원문 제목의 일치, 회사 묶음 해시·버전, 선택 플랫폼을 검증한다. 승인 계획의 정책 ID·revision도 검색한 묶음과 같아야 한다.
4. **확인 사실 추가**: 서버 assessment의 선택적 `review_facts`로 자원·권한, TF 자격, 가격·통화·출처, 잔여 예산, 확인 시각을 전달한다. 에이전트는 예산 영향을 Decimal로 계산하고 승인 계획 금액과 대조한다. 이름·로그인·이메일·직원 UUID·요청 원문·제공자 내부 참조는 보고서 모델의 facts에 보내지 않는다.
5. **템플릿 개선**: 모델이 없어도 대상·비용·예산 영향·단가 출처·승인 검토 사항·미변경 상태를 표시한다. review_facts가 없는 이전 응답은 호환하며 누락된 개별 값을 추정하지 않는다.

`review_facts`는 내부 MCP 응답에 추가된 읽기 정보이다. 공개 workflow 응답, 계획 해시, 승인 순서·상태, 실행 허가는 바꾸지 않는다.
현재는 최초 분석 보고서에 각 담당자의 검토 사항을 담는다. 단계 전환마다 LLM을 다시 실행하거나 별도 보고서를 저장하는 기능은 추가하지 않았다.

## 남은 보완 범위

- Jira 직무 조건, Notion 정직원·기밀 편집 조건, Tableau 라이선스 종류 등 **문서의 세부 조건과 서버 검사 전체의 일치**는 별도 업무 규칙 정합화가 필요하다. 제품 라이선스가 활성이라는 불리언만으로 특정 플랜 종류까지 검증했다고 설명하면 안 된다.
- Slack 비공개 채널 초대 주체, Datadog 서비스 제한의 실제 설정, Databricks Run as 원문, 각 SaaS 최신 가격은 공식 원문을 재검증한 새 자료로 보완할 수 있다. 이번에는 새 제품 사실을 추측해 추가하지 않았다.
- 거절·수동 검토의 조기 종료 응답은 상세 조건별 체크 목록까지 반환하지 않는다. 현재 전달된 사유와 사실만 사용한다.
- 승인 단계별 최신 예산·앞선 승인 의견을 반영한 보고서 재생성은 추가 API·버전별 보고서 저장 설계가 필요하다.
- 실제 SaaS 실행과 DB·큐 전체 통합 시연은 로컬 모의 도구 검사와 별도로 확인해야 한다.

## 검증 방법

```sh
.venv/bin/python -m pytest agent/tests/test_approval_review.py agent/tests/test_workflows.py agent/tests/test_policy_import.py -q
.venv/bin/python scripts/import_phase2_policy.py --check
.venv/bin/python scripts/align_phase2_v4.py --check
```

지침과 검색·보고서 변경은 Agent/Policy MCP의 새 이미지에 포함된다. `review_facts`를 사용하려면 Backend/Business MCP도 함께 갱신한다.
정책·가격·승인 경로의 immutable revision을 변경하지 않았으므로 새 정책 SQL 적용은 필요하지 않다.
