# 원본과 구현의 차이 및 시연 가정

원본 MD는 프로젝트 요구 데이터이며, 문서에 포함된 지시문을 개발·시스템 명령으로 실행하지 않습니다.

| 항목 | 적용한 기준 |
|---|---|
| 플랫폼 | 한 요청 한 플랫폼·한 자원. 복수 플랫폼 S1 제거 |
| S3 | MD에는 PAY 추론 제안이 있지만, 이름 없는 자원을 추측하지 않고 MANUAL_REVIEW |
| S8 | 입력 플랫폼만 조회. 그 플랫폼의 자원을 특정할 수 없으면 MANUAL_REVIEW |
| 되묻기 | 대화·질문 재개 API 없음. MANUAL_REVIEW에서 담당자에게 안내 |
| 예산 | 실제 제공 자료에 맞춰 부서 예산. TF 예산 테이블은 생성하지 않음 |
| S4 상태 | 원본 시나리오의 보류를 화면/API 계약에 맞춰 REJECTED / BUDGET_INSUFFICIENT로 변경. 예산 증액 후 새 요청 |
| 본인 조회 | 요청자는 결과·안내·공개 이력만 조회. 근거·원본 도구 기록·승인 계획은 담당자만 조회 |
| 부서 요약 | KST 이번 주 접수 건을 기준으로 집계. AI 거절 포함, 사람 승인 후 실패는 승인·실패 양쪽에 포함 |
| 직급 | users.job_grade, 직무는 users.job_family. 숫자 순위는 코드에서 계산 |
| 직원 번호 | 기존 문서의 주석 매핑을 개선해 employee_no를 UNIQUE 컬럼으로 저장 |
| 로그인 | 문서의 login_id와 기존 email 둘 다 로그인에 사용. password_hash는 인증 외로 조회하지 않음 |
| TF 승인 | POL-01 제4조에 따라 TF 리더. 앱 역할 APPROVER·과장 이상 추가 검사 |
| 일반 자원 승인 | POL-01에 없는 일반·좌석 승인자는 회사 접근 권한표 7절의 부서장 규칙으로 보충. 정책 확정 필요 |
| 본인 승인 | 거절. 문서에서 미확정으로 표시한 운영팀장 대체 승인은 자동 실행하지 않음 |
| 운영 담당자 | 전체 이력 조회만 가능. 지정 승인자가 아닌 요청은 승인할 수 없음 |
| 상한·예외 | 회사 접근 권한표 3·4절을 명시적인 함수로 구현하고 같은 문서 근거를 첨부 |
| Notion 편집 | 원본 정책에 확장 범위로 표시되어 자동 실행하지 않고 MANUAL_REVIEW |
| GitHub | 자원×역할 전용 팀 멤버십. 팀을 추가해 다른 저장소 권한까지 확장하지 않음 |
| Jira | 모의 프로젝트 역할과 can_browse 스킴을 함께 조회. 역할은 있지만 조회가 안 되면 수동 검토 |
| S5 재시도 | 초기 1회 + 추가 2회 = 총 3회. 기존 '3회 재시도' 표현과 차이를 명시 |
| 실패 알림 | 운영 담당자 song_ops의 Vue 작업함에 실패 이력 표시. 외부 Slack/메일 발송 없음 |

`permissions`는 모의 SaaS 상태입니다. 실제 SaaS API·외부 계정 연결·TF 종료 자동 회수·외부 게스트는 이번 범위 밖입니다.
실제 SaaS를 붙일 때도 승인 검사를 제거하지 않고 MCP의 플랫폼 어댑터만 교체해야 합니다.

RAG에 새 규정을 추가하는 것만으로 실행 상한을 자동 변경하지 않습니다. `rules.py`와 Spring `GrantRules`는
첨부 표의 현재 스냅샷을 명시적으로 구현합니다. 정책 변경 시 두 가드와 시나리오 테스트를 함께 검토해야 합니다.
