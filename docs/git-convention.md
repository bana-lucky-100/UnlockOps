# UnlockOps Git 컨벤션

이슈 번호를 포함하는 브랜치·커밋 형식을 기준으로 정리한 협업 규칙입니다. `add`는 단순 추가, `feat`는 기능 구현에 사용합니다. 팀 합의가 바뀌면 해당 절을 수정합니다.

이 문서는 브랜치·커밋·PR 규칙의 기준 문서입니다. 제목 검사나 병합 조건을 자동으로 강제하는 설정은 별도로 추가해야 합니다.

## 1. 기본 작업 흐름

1. 이슈를 만들고 목표와 할 일을 작성합니다.
2. 최신 `main`을 기준으로 작업 브랜치를 만듭니다.
3. 작업 내용을 목적별 커밋으로 나누고, 변경한 영역에 맞는 검증을 수행합니다.
4. `main`을 대상으로 PR을 만들고 관련 이슈를 연결합니다.
5. 작성자가 아닌 팀원에게 리뷰를 요청하고 의견을 반영합니다.
6. 리뷰와 필요한 검증을 마친 뒤 병합하고 작업 브랜치를 정리합니다.

## 2. 작업 유형

브랜치·커밋·PR에 아래 유형을 공통으로 사용합니다. 파일을 새로 만들었는지보다 변경의 주된 목적을 기준으로 선택합니다.

| 유형 | 사용 시점 | 예시 |
| --- | --- | --- |
| `add` | 기능 동작을 구현하지 않는 파일·리소스의 단순 추가 | 데모용 샘플 데이터, 이미지 추가 |
| `feat` | 새 기능 구현 또는 기존 기능 확장 | 접근 요청 화면, 승인 API, Agent 기능 구현 |
| `fix` | 의도와 다르게 동작하는 오류 수정 | 승인 상태 조회 오류 수정 |
| `docs` | 문서만 추가·수정 | README, Git 컨벤션, 실행 안내 작성 |
| `refactor` | 동작을 유지하는 코드 구조 개선 | Agent 상태 처리 로직 분리 |
| `test` | 테스트 추가·수정 | 승인 흐름 통합 테스트 추가 |
| `chore` | 개발 환경·도구·의존성·자동화 설정 | .gitignore, 공통 서식, 패키지, 워크플로 설정 |

기능과 그 기능에 필요한 테스트·문서를 함께 추가한 경우 주된 목적에 맞춰 `feat`를 사용합니다. 문서, 테스트, 개발 환경 설정은 각각 `docs`, `test`, `chore`를 사용합니다. 브랜치 안의 개별 커밋은 각 변경 목적에 맞게 다른 유형을 사용할 수 있습니다.

## 3. 브랜치 이름

```text
<유형>/#<이슈번호>-<짧은-영문-설명>
```

- `main`은 팀이 공유하는 기준 브랜치로 사용합니다.
- 작업 브랜치는 하나의 이슈 또는 함께 검토할 수 있는 작업 범위로 나눕니다.
- 설명은 영문 소문자와 하이픈을 사용합니다.
- 브랜치의 이슈 번호와 연결할 작업 이슈를 일치시킵니다.

```text
feat/#12-access-request
fix/#13-approval-status
docs/#14-git-convention
chore/#15-dev-environment
add/#16-demo-resources
```

터미널에서 브랜치 이름을 사용할 때는 따옴표로 감싸면 안전하게 전달할 수 있습니다.

```sh
git switch -c 'feat/#12-access-request'
```

위 명령은 브랜치 생성 예시입니다. 실제 작업 전에는 변경 사항을 보관하고 최신 `main`을 기준으로 준비합니다.

## 4. 커밋 메시지

```text
<유형>/#<이슈번호>: <변경 내용>
```

- 유형은 소문자로 작성하고, 콜론 뒤에는 공백 한 칸을 둡니다.
- 제목은 변경 결과를 알 수 있는 한 줄로 작성합니다. 설명은 한국어로 작성해도 됩니다.
- 한 커밋에는 함께 검토하고 되돌릴 수 있는 변경을 담습니다.
- 이유나 주의할 점이 필요하면 제목 다음 한 줄을 비우고 본문에 작성합니다.
- 비밀값, 로컬 환경 파일, 생성된 색인·캐시·빌드 결과는 커밋하지 않습니다.

```text
feat/#12: 접근 요청 화면 구현
fix/#13: 승인 상태 조회 오류 수정
docs/#14: Git 컨벤션 정리
chore/#1: 공통 개발 환경 설정 및 협업 가이드 추가
add/#16: 데모용 정책 샘플 데이터 추가
```

본문을 포함하는 예시는 다음과 같습니다.

```text
fix/#13: 승인 상태 조회 오류 수정

승인 완료 후 화면에서 이전 상태를 표시하던 문제를 수정한다.
처리가 끝나면 최신 데이터를 다시 조회하도록 변경한다.
```

## 5. 이슈 작성

- 새 기능은 [Feature 템플릿](../.github/ISSUE_TEMPLATE/feature.md)을 사용합니다.
- 제목은 템플릿의 `[Feature]` 표시 뒤에 작업 목표를 작성합니다. 예: `[Feature] 접근 요청 화면 구현`
- `What is this issue?`에는 배경과 목표를, `Progress`에는 완료 여부를 확인할 수 있는 작업을 작성합니다.
- 작업 진행에 맞춰 체크리스트를 갱신합니다.
- 자동 담당자 지정 워크플로가 활성화되면 작성자가 Assignee로 지정됩니다. 이미 지정된 담당자는 유지됩니다.

현재 Feature 템플릿은 `enhancement` 라벨을 사용합니다. 라벨이 없다면 GitHub에서 생성해야 합니다. 추가 이슈 유형과 라벨은 팀 합의 후 템플릿에 반영합니다.

## 6. PR 작성

PR 제목도 커밋과 같은 형식을 사용합니다.

```text
feat/#12: 접근 요청 화면 구현
```

본문은 [PR 템플릿](../.github/pull_request_template.md)의 항목을 따릅니다.

| 항목 | 작성 내용 |
| --- | --- |
| Related issue 🛠 | 관련 이슈 번호와 자동 종료 여부 |
| Work Description ✏️ | 주요 변경 내용, 변경 이유, 확인 방법과 결과 |
| Screenshot 📸 | 화면 변경 이미지·영상. 해당 없으면 `N/A` |
| Uncompleted Tasks 😅 | 남은 작업을 체크리스트로 작성. 없으면 `N/A` |
| To Reviewers 📢 | 중점 확인 사항·논의할 내용. 없으면 `N/A` |

관련 이슈를 완료하는 PR은 다음과 같이 작성합니다.

```text
Closes #12
```

기본 브랜치인 `main`을 대상으로 병합될 때 이슈가 자동으로 닫힙니다. 작업을 완료하지 않고 참조만 할 때는 `Related to #12`로 작성합니다. 여러 이슈를 완료하면 각 이슈에 `Closes`를 붙입니다.

PR에는 변경한 서비스의 실제 검증 결과를 적습니다. 문서 수정은 링크와 내용 확인 등 변경에 맞는 검증을 기록하고, 실행하지 못한 검사가 있다면 이유를 함께 적습니다.

## 7. 리뷰와 병합

- 작성자가 아닌 팀원 1명 이상의 리뷰를 권장합니다.
- 리뷰 요청 시 중요한 변경과 확인이 필요한 부분을 `To Reviewers`에 적습니다.
- 리뷰 의견을 반영하고, 실행 가능한 검사에서 문제가 없는지 확인한 뒤 병합합니다.
- 기본 병합 방식으로 **Squash and merge**를 권장합니다. 최종 커밋 제목도 이 문서의 커밋 형식에 맞춥니다.
- 병합이 끝난 작업 브랜치는 정리합니다.
- 공유 브랜치의 커밋 이력을 다시 쓰는 작업은 관련 팀원과 먼저 합의합니다.

리뷰 필수, 직접 푸시 제한, 병합 방식은 GitHub 저장소 설정에서 별도로 적용해야 합니다. 이 문서를 추가하는 것만으로 설정이 변경되지는 않습니다.

## 8. 규칙을 수정할 때

브랜치·커밋 형식은 2~4절, 이슈·PR 양식은 5~6절, 리뷰·병합 방식은 7절에서 관리합니다. 양식 자체를 바꾸면 `.github`의 실제 템플릿도 함께 수정합니다.

[협업 안내](../CONTRIBUTING.md)는 코드·환경 설정과 PR 전 확인 사항을 관리합니다. Git 규칙을 바꿀 때는 이 문서를 먼저 수정하고, 연결된 문서의 설명도 맞춥니다.
