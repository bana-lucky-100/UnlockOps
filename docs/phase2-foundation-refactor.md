# Phase 2 준비: 상태 계약 통일과 승인 책임 분리

> 통합 전 설계·정책 해석 기록입니다. 현재 실행 구조는 [업무 실행 구조](architecture.md), 최신 변경·검증은 [구현 기록](../IMPLEMENTATION.md)을 따릅니다.

## 변경 목적

Phase 2의 2단계 승인과 권한 회수를 추가하기 전에 현재 구현의 두 가지 결합을 줄였습니다.
서버에서는 검토 중인데 화면에서는 완료로 해석하던 상태 불일치를 해소하고,
사람의 승인 기록과 권한 실행 전환을 별도 책임으로 분리했습니다.
현재 서비스는 여전히 단일 플랫폼·단일 자원·1회 승인으로 동작합니다.

## 1. 처리 상태와 완료 결과 구분

기존에는 안내 성공도 `MANUAL_REVIEW / RAG_GUIDANCE`로 저장했습니다.
프론트가 사유 코드와 본문 유무를 확인해 완료로 바꾸어 표시했기 때문에 서버와 화면의 의미가 달랐습니다.

상태 8개는 유지하고 `result_type`을 Python 결과 모델, Java 수신·저장·응답 모델, DB, 프론트 타입에 추가했습니다.

| 상황 | status | result_type | verification_ok |
|---|---|---|---|
| 안내 제공 완료 | DONE | GUIDANCE | null |
| 실제 권한 반영 확인 | DONE | ACCESS_VERIFIED | true |
| 진행·승인 대기·수동 검토·거절·실패 | 각 기존 상태 | null | 기존 경로에 따름 |

- `status`: 워크플로우 처리 상태입니다.
- `result_type`: 성공적으로 완료한 대상입니다. 안내와 실제 권한 반영을 구분합니다.
- `reason_code` / 큐의 `reasonCode`: 판정·실패의 구체적 사유입니다.

안내 완료는 문제 해결이나 권한 변경 성공을 뜻하지 않습니다. 안내에는 본문이 필요하고 실행 계획과
권한 검증 값은 없어야 합니다. 실행 작업은 GUIDANCE로 완료할 수 없고, 기존의 권한 검증과 실행 영수증이 필요합니다.
근거 부족·안내 생성 실패는 MANUAL_REVIEW로 남습니다.

프론트의 목록 분류와 폴링은 status를 따릅니다. result_type은 안내 완료 라벨·상세 구성에 사용합니다.
요청자는 기존처럼 간략한 진단을 보고, 긴 안내 본문은 승인자에게 표시합니다.
원본 감사 이벤트의 과거 안내 표현만 호환 처리하며 현재 요청의 상태를 사유 코드로 추측하지 않습니다.

### 기존 데이터 호환

`V5__completion_result_type.sql`이 유효한 과거 안내 성공을 DONE / GUIDANCE로 변환하고 기존 DONE에
ACCESS_VERIFIED를 부여합니다. 빈 안내 본문은 완료로 바꾸지 않습니다. DB CHECK로 완료 유형과 검증 조건을 강제합니다.
원본 감사 이벤트는 보존합니다. 과거 큐 메시지·체크포인트는 result_type 필드가 없을 때 입력 경계에서 정규화합니다.

배포는 **새 서버와 V5 적용 → 새 worker·프론트** 순서입니다. 새 서버는 구 메시지를 받을 수 있지만,
구 서버는 새 안내 완료 메시지를 권한 검증 없는 DONE으로 거부합니다. 혼합 버전 서버 운영은 피해야 합니다.

## 2. 승인 기록과 실행 전환 분리

기존 `ProblemService.decide()`가 담당하던 승인 검증·기록·실행 큐 등록을 다음과 같이 나눴습니다.

| 구성 | 책임 |
|---|---|
| ProblemService | 요청 접수 및 조회 |
| ApprovalDecisionService | 지정 승인자·본인 승인 금지·카드 해시·최신 자격 검증, 승인·반려 기록과 이력 저장 |
| ApprovalCompletionPolicy | 현재 필수 승인인 1회 사람 승인 완료 여부 판단 |
| ApprovedExecutionService | 저장된 승인 재조회, 승인자·계획 해시·실행 키 검증, EXECUTING 전환과 EXECUTE Outbox 등록 |

승인 결정은 먼저 기록하고, 실행 서비스가 같은 트랜잭션에서 저장된 기록을 다시 잠금 조회합니다.
승인이 완료되지 않았으면 대기 상태를 유지하고 실행을 등록하지 않습니다.
계획이나 실행 키가 불일치하면 실행을 차단합니다. 이미 EXECUTING이면 실행 작업을 중복 등록하지 않습니다.

승인 결정·감사 이력·실행 전환·Outbox는 모두 함께 커밋하거나 롤백합니다.
실행 서비스는 MANDATORY 전파를 사용하므로 기존 트랜잭션 없이 단독 호출할 수 없습니다.
반려 사유 필수, 본인 승인 금지, 승인 직전 최신 자격 확인, 부여 직전 재검증은 유지했습니다.
기존 decision HTTP API 입력·응답도 유지했습니다.

### Phase 2에서 이어서 할 일

이번 작업은 다단계 승인 자체를 구현하지 않습니다. 단계별 승인 테이블·담당자 배정·보고서는 아직 추가하지 않았습니다.
Phase 2에서는 단계별 기록을 도입하고 ApprovalCompletionPolicy가 모든 필수 단계의 완료를 확인하도록 확장해야 합니다.
그에 맞춰 결정 검증·다음 승인자 배정·실행 직전 서버 검증도 확장해야 합니다.
권한 회수·정책 기준 통일·승인 보고서 분리는 이번 범위에 포함하지 않았습니다.

## 검증

- 에이전트·MCP: 321개 테스트 통과.
- 백엔드: 전체 소스와 테스트 컴파일 통과. 기존 POM 의존성으로 JUnit 엔진을 직접 실행해 138개 테스트 통과.
- 프론트: 안내 완료 계약·요청 멱등성 테스트 16개 통과.
- 회귀 테스트 추가: 안내 완료의 큐→DB→HTTP 일치, 구 메시지 호환, 승인 후 Outbox 실패 시 전체 롤백,
  V4→V5 마이그레이션 및 완료 조건 CHECK 검증.
- 미실행: Docker가 가동되지 않고 로컬 PostgreSQL도 공유 메모리 권한 제한으로 시작하지 못해 DB·RabbitMQ 통합 테스트는 미실행.
- 프론트 전체 테스트·빌드: 필요한 Vue/vue-tsc 의존성이 캐시에 없고 외부 다운로드가 차단되어 미완료.
- Maven 표준 test 실행은 Surefire 의존성 다운로드 제한으로 미완료이며, 위 백엔드 테스트는 동일 프로젝트 클래스패스의 JUnit 직접 실행 결과입니다.
